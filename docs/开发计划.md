## 〇、开工前先认清三件事

### 1. 这个项目不是「再做一遍教程项目」

参考项目已经把 **安全执行** 做透了（工具注册表、计划校验、乐观锁、幂等队列、快照撤销），但 **可解释性** 几乎为零（无 CoT 流式、无反思循环、无 trace、无规划评测）。

你的 README 已经宣称了两条它给不了的能力：

| README 宣称 | 参考项目 | 你要怎么做 |
|---|---|---|
| 「LangGraph 图结构状态机」 | 只有 `plan → verify` 直线，**无条件边、无循环、无 checkpointer** | 自建带条件边的图 + 反思循环 + Postgres checkpointer |
| 「SSE 推送 Agent 思维链（CoT）」 | **完全没有**，SSE 只推 `progress/stage` | 新增 `cot` 事件类型，与进度流并行推送 |

**这两条是项目的技术制高点，也是面试时唯一能压过参考项目的东西。** 其余 7 条能力都有成熟实现可照搬。

### 2. MVP 边界要提前划清

```
M1 ──────────────── M8 ────────┐ M9 ────────── M10 ──── M11
│      能用的产品（照抄为主）      │ │  差异化三件套  │ 工程化 │ 功能补齐
└──────── MVP，必须先跑通 ────────┘ └── 加分项，简历杀手锏 ──┘
```

**纪律：M9 之前不许碰差异化功能。** 参考项目的教训是「先把安全的链路做扎实，再谈智能」——反过来做会得到一堆会失控的花哨功能。

唯一的例外是 **SSE 事件协议**：在 M2 定义协议时就把 `cot` / `plan` / `reflection` 事件类型**预留出来**（可以先不发，但字段结构定死）。否则到 M9 再加，前端解析层要返工。

### 3. 参考项目是蓝本，不是模板——照抄清单和禁止清单

**照抄（省掉全部试错成本）**

| 模式 | 参考位置 | 成本 |
|---|---|---|
| run id 直接作为 ARQ job id 去重 | `queue.py` | 10 min |
| `agent_hidden` 隐藏内部 ID，服务端回填 | `tools/base.py` + `agent/llm.py` | 1 h |
| Pydantic Model → OpenAI function schema | `agent/llm._schema_of()` | 2 h |
| 服务端计划校验（存在性/合法性/依赖/环检测/长度） | `agent/plan.py` | 1 d |
| 统一执行外壳（状态流转 + 分级异常 + 推进下一步） | `services/tools.execute()` | 0.5 d |
| revision 乐观锁让选区/遮罩失效 | `services/selections.py` | 0.5 d |
| before/after 快照式 undo/redo | `edit_history` | 1 d |
| mock provider 分层（Protocol，非 ABC） | `providers/base.py` | 0.5 d |
| SAM embedding LRU 缓存（上限 4 + Lock） | `edits/segment.py` | 0.5 d |
| 测试独占 Redis DB 1 + `test_` 前缀用户定向清理 | `conftest.py` | 0.5 h |

**禁止照抄（参考项目的历史包袱）**

| 别抄 | 原因 | 你的做法 |
|---|---|---|
| 前端硬编码 `ACTION_LABELS` / `UNDOABLE` | 后端 22 spec + 前端 23 标签 + 11 UNDOABLE，**三份手工维护必然漂移** | M4 就做 `/api/tools` 元数据端点，前端标签由注册表驱动 |
| `jwt_secret` / S3 弱口令默认值 | 缺配置时静默用不安全默认值，把「配置没传」伪装成「配置传了但不对」 | 必填变量 fail-fast：缺失即抛错，不给默认 |
| 评测只覆盖像素工具 | 规划质量无人度量 | M10 做 `{指令 → 期望工具序列}` 评测集 |
| `lru_cache` 全局单例 | conftest 手动逐个 `cache_clear()`，脆 | 用 FastAPI `Depends` + 生命周期管理，或集中一个 `deps.py` 暴露清理函数 |
| CanvasStage 1087 行巨型组件 | 逻辑与渲染耦合，无法单测 | domain 层（`layerDoc/transform/selection/history`）先抽出来 |
| 无 CI | 本地能跑但无人验证 | M10 上 GitHub Actions |

### M1 · 后端骨架 + 鉴权 + 素材存储 ✅ 已完成（2026-10-12）

**实现要点**（与初版设想的差异都是踩出来的）

| 主题 | 落地方式 | 原因 |
|---|---|---|
| 密码哈希 | `sha256 → base64 → bcrypt(rounds=12)` | bcrypt 只吃前 72 字节，直接喂长密码会被截断；预哈希归一到 44 字节后支持任意长度 |
| 安全失败 | 未知邮箱与错误密码返回**同一句**提示 | 避免通过响应差异枚举账号；用户不存在时也走一次校验，避免时序侧信道 |
| 素材 URL | 库存 `s3_key`，对外一律**预签名临时 URL** | 桶保持私有；换域名/换存储不需要洗数据 |
| 文件校验 | 按 **magic bytes**（Pillow `verify`）定类型，不信 mime/扩展名 | 改后缀就能绕过客户端声明的类型；伪装成 png 的脚本文件必须被拦 |
| 素材 URL 访问 | 别人的资源返回 **404 而非 403** | 403 会泄露「该资源存在」 |
| 迁移正确性 | 测试用 `create_all`（快），主库用 `alembic upgrade head`（验脚本） | 两条路互为补充：前者隔离，后者保证迁移脚本本身没错 |

**传输通道抽象（为 M6 的选区大图预留）**

上传做成两段式契约：**拿 ticket → 按 method 上传 → confirm**。两种模式共用同一份
`UploadTicket` 结构，`ASSET_UPLOAD_MODE` 一个配置项即可在「后端直传」与「预签名直传」间切换，
**前端零改动**（`frontend/src/domain/upload.ts` 是唯一分叉点）。MVP 先用 backend。

### M2 · Provider 抽象 + ARQ + SSE ✅ 已完成（2026-10-12）

**实现要点**（与初版设想的差异都是踩出来的）

| 主题 | 落地方式 | 原因 |
|---|---|---|
| Provider 抽象 | `typing.Protocol` + `@runtime_checkable`，实现类不 import 基类 | 结构化子类型：换实现时少一处耦合；协议一致性由测试 `isinstance` 守住 |
| Provider 返回值 | 一律 **bytes**，绝不返回 URL | 上游 URL 有有效期（百炼 24h），落库即烂数据；转存自有 S3 是 Provider 内部的职责 |
| 未接入的实现 | `get_image_provider()` 对非 mock 直接 **RuntimeError** | 静默回退 mock 是最危险的兜底：线上会一直出占位图且没有任何报错 |
| 入队幂等 | `enqueue_job(task, run_id, _job_id=str(run_id))` | job id 相同 → ARQ 只保留一个。前端重试/网关重放/用户狂点都不会重复扣费 |
| 订阅时序 | `subscription()` 写成 **asynccontextmanager**：进入上下文时订阅已完成 | 裸 async generator 无法保证「先订阅、后发快照」，任务可能在两步之间结束，连接永远空等 |
| 坏帧处理 | 单帧解析失败只跳该帧，不断开 | 一次序列化 bug 不该让整条流死掉；与前端 `try/catch` 同策略 |
| 取消 | `cancel()` 主动推一帧 `done` | 取消在另一个请求里触发，worker 侧不会产生任何事件；少了这帧前端要等到超时 |
| prompt 校验 | `min_length=1` **之外**再 trim 后判空 | 一串空格照样能过 `min_length`；trim 也保证「看着一样」的 prompt 出同一张图 |
| 前端订阅 | 原生 `EventSource`（不是 fetch 流） | 自动重连是它的核心能力，后端 600s 主动断开正是靠它接回去 |

**协议先行的兑现**：`schemas/events.py` 与 `frontend/src/domain/events.py` 各自定义了完整的
9 类事件，`cot` / `plan` / `step` 本阶段**后端不发**，但字段结构已定死 —— M8（多步计划）与
M9.1（思维链）直接启用即可，前端解析层不用返工。

**实测结果**：worker 真实执行文生图 0.73s，产物进对象存储并落 `assets` 表，
SSE 收到 `snapshot(succeeded)` + `done` 完整两帧。后端测试 **79 项全绿**，ruff 无告警。

**信息架构对齐（M2 收尾补的）**：初版把 UI 做成了「素材库页 + 生图页」各写一份 header，
这里统一为三层布局路由 `ProtectedRoute → WorkbenchLayout → 页面`：

| 路由 | 页面 | 为什么这样切 |
|---|---|---|
| `/` | 落地页 | **公开**：销售页不该先要求登录，也不套工作台外壳 |
| `/create` | 创作 | 生成 + 上传 + 历史素材**一屏**——同一次创作的三个入口，拆开会让人先迷路 |
| `/candidates/:runId` | 候选图 | run id 在 URL 上才谈得上刷新恢复与分享；**必须配 `GET /runs/{id}/assets`** |
| `/assets` | 素材库 | 全量管理页；上传不再重复一份，只留跳转 |
| `/editor` | 编辑 | M3 起填充 |

落地页输入框会把 prompt 一路带到创作页（未登录先去登录页并携带 `{next, prompt}`），
不在两个页面重复输入同一句。
能力卡片带 `ready` 标记，未上线的能力打「即将上线」——
**落地页不宣称还没做出来的功能**，演示时被追问会很尴尬。

**UI 基线（M2 收尾补的）**：初版控件全部手写——原生 `<select>`、手拼 SVG 图标、
各页自定字号，页面拆开看没毛病、放一起明显不是一套东西。整改后全站接入 **antd 6**
（`@ant-design/icons@6`，React 19 原生支持、无需补丁），并立了三条规矩：

| 规矩 | 内容 | 为什么 |
|---|---|---|
| 主题单一真源 | `index.css` 的 Tailwind token ↔ `lib/antdTheme.ts` 的 antd token 一一对应 | 两边各调各的，antd 组件和手写部分会一眼两套系统 |
| 主色只有一个例外出口 | 确需非主色主按钮时用局部 `ConfigProvider` **只包住那一个按钮**，主题对象放在 `lib/antdTheme.ts` 导出 | 主色的语义是「整页最该点的那一下」，出现两个主色层级就崩了 |
| 不留原生 form 控件 | `<select>` / `<input>` / `<textarea>` / `<button>` 全部换成 antd 件 | 原生下拉面板由操作系统自绘，永远和主题对不上 |

顺带收敛了三处重复的素材卡（创作页历史素材 / 素材库 / 候选页）为 `components/AssetCard`，
一次大部件的圆角调整不必再改三遍。构建按 `react` / `antd` / 业务代码分块，
改业务逻辑不应让用户重新下载整个组件库。

配套后端改动：`asset_service.list_assets_by_ids()` 按传入顺序返回并限定本人，
新增 `GET /api/runs/{run_id}/assets`。
**分工原则**：REST 负责现场恢复，SSE 只负责实时增量 —— 事件流从不做唯一数据源。

### M3 · 编辑会话 + LayerDocument + Konva 画布
**参考提交**：`e2c84f5` 编辑会话与画布骨架 / `96f6168` 切回恢复图层文档
**工作量**：4–5 人天（前端占大头）

| 项 | 内容 |
|---|---|
| 产出 | `edit_sessions` / `session_assets` 表、LayerDocument JSONB、前端 Konva 画布 + 图层面板、切换当前图 |
| 关键设计 | ① **工具只改 JSONB 文档，像素合成由渲染层完成**（声明式）；② `resolve_layer()` 支持按 id **或按图层名**查找，未指定取「最上层可见图像层」——这个默认值同时服务 UI 和 Agent，两边行为必须一致；③ 前端 `domain/layerDoc.ts` 先写，组件只消费 |
| 验收 DoD | ① 上传的图能在画布渲染；② 多张候选图可切换为当前图；③ 图层面板正确列出层级；④ 刷新页面后画布状态完整恢复 |

**M3.1 后端地基（已落地）**：`edit_sessions` / `session_assets` 表 + 迁移、
`LayerDocument` pydantic 结构、`resolve_layer()`、会话 CRUD。122 项测试全绿。

| 主题 | 落地方式 | 原因 |
|---|---|---|
| 文档 vs 像素 | JSONB 存**结构**，像素由前端 Konva 实时合成 | 任意一步可逆（改回字段值即可），且 Agent 与 UI 消费同一份状态 |
| layers 顺序 | 数组**从下到上**（index 0 最底），面板渲染倒序 | 存的时候倒序会让「索引」和「视觉层级」相反，后面每个按索引写的工具都要脑内翻转 |
| id / name 唯一性 | id 必须唯一；name 允许重复，按名查找取**最上层** | 同一张素材插两次很常见，禁重名会让这类操作先算新名字，收益不抵复杂度 |
| 图层定位 | `resolve_layer()` 唯一入口，找不到就抛错 | UI 选中态与 Agent 工具调用共用一套规则；静默 fallback 到「第一层」会让用户以为改了 A 实际改了 B |
| 文档内的资产引用 | 只放 `asset_id`，绝不入预签名 URL | 桶私有 + URL 有有效期，落进去就是注定过期的烂数据 |
| session_assets 独立表 | 不靠解析 JSON 提取 asset_id | 级联删除、按素材反查会话都需要它；否则要全表扫 JSONB 且容易漏 |
| 候选图初始状态 | 建会话时只有**第一张**可见，其余 hidden | 多张叠上去画布只看得见最上面那张；一旦建好，可见性完全由文档决定 |
| 文档写入 | 整份替换（`PUT /doc`），不做局部 patch | 层级增删后状态是多个图层共同决定的，patch 语义表达不了；乐观并发留到 M4 |
| 坏文档防线 | HTTP 边界用 pydantic 校验，422 不进库 | 文档一旦写坏，前端渲染与后续所有工具全废，且没有第二道校验点 |

> `ToolRun` 与 `EditSession` 刻意分开：前者是**单次任务**（秒级、有终态），
> 后者是**工作现场**（可能开几天）。用 `tool_runs.session_id` 关联即可，
> 混在一起会让任务列表里出现一堆永远不结束的东西。

**M3.2 前端画布（已落地）**：`domain/layerDoc.ts`（纯函数 + vitest）、CanvasStage、
LayerPanel、`/editor` 索引 + `/editor/:sessionId` 详情。四条 DoD 全过。

| 主题 | 落地方式 | 原因 |
|---|---|---|
| 领域层先写 | `domain/layerDoc.ts` 与后端逐字段对齐，组件只调用 | UI 选中态与 Agent 工具调用共用一套规则；规则写进组件就再也没法给另一头用了 |
| 面板顺序 | 数组翻转（bottom-up → top-down）**只允许在 LayerPanel 一处发生** | 两处各翻一次等于没翻，而且很难发现；画布那头直接用数组顺序 |
| 画布与面板的关系 | 都是文档投影，编辑会话状态**不在 store 里留第二份** | 藏一份「真正被编辑的东西」之后，刷新到底以谁为准永远说不清 |
| 写回服务端 | 乐观更新 + 失败回滚（invalidate） | 切个图层还要等一轮 HTTP 太钝；但失败必须回到服务端真实状态，否则用户看到的是幻觉 |
| 入口 | 候选页「在画布中编辑」、素材卡「编辑」，统一走 `useCreateSession` | 两处各写一遍的结果是跳转目标与失败处理都不一样 |
| `/editor` | 索引页列会话，详情必须是 `/editor/:sessionId` | session id 在 URL 上才谈得上刷新与分享，与候选页同一个道理 |
| 打包 | Konva 走 `React.lazy`，编辑路由才加载 | 330KB（gzip 100KB）不该让只看落地页的人付带宽 |

> 切一张候选图不该顺手把用户自己加的文字也藏了）。真正的编辑工具从 M4 起接入。

### M5 · 确定性工具 + 快照式撤销
**参考提交**：`3dfa8a0` 确定性工具 + 线性撤销 / `249c69e` 调色保留透明通道
**工作量**：3 人天

| 项 | 内容 |
|---|---|
| 产出 | 裁剪/翻转/层级/透明度/调色等轻工具（同步 REST）、`edit_history` before/after、undo/redo |
| 关键设计 | ① 轻工具走**同步 REST**（只改 LayerDocument），重像素工具走 ARQ —— 别混；② 每条历史存 `params.before` + `result`，undo 取 before、redo 取 result；③ 新操作先 `DELETE WHERE seq > history_seq` 截断重做分支；④ 调色拍平**必须保留 alpha 通道**，否则结果发黑；⑤ 「结果只进图片墙」时画布没变，但仍要留一条历史记录，否则用户在编辑记录里找不到这次生成 |
| 验收 DoD | ① 连续操作后能一路 undo 回初始态，redo 能重放；② undo 后新操作正确截断 redo 分支；③ 带透明通道的图调色不发黑 |

**已落地（M5.1 后端 + M5.2 前端）**：`edit_history` 表、快照式 undo/redo、
`crop_layer` / `reset_crop` / `flip_layer` 三个新工具（注册表累计 16 个）、
`Layer.crop` 与 `Transform.flip_x/flip_y`、前端补上此前「只读不画」的
adjustments / crop / flip 渲染。后端 169 项测试、前端 32 项 vitest 全绿。

| 主题 | 落地方式 | 原因 |
|---|---|---|
| 快照式而非反向操作 | 每条历史存 before / after 两份整文档 | 反向操作要为 16 个工具各写一份严格对称的 undo，任何一处不对称都会悄悄改坏文档，且难以复现 |
| 文档与历史同一事务 | 工具统一走 `history.apply_tool_calls()`，不用 `replace_doc()` | 后者自己会 commit，把「写文档」和「写历史」劈成两个事务 |
| `history_seq` 指针 | 会话上挂一列，文档始终表示当前状态 | 有了它 redo 就是 seq+1，新操作只需删掉指针之后的记录；比另建一条 redo 链表简单 |
| 上限 50 条且不重排 seq | 丢最老的，seq 保持绝对递增 | 重排会让指针一夜之间指向别的条目；撤到边界停住比撤到错误中间态好 |
| `changed=False` 照样留记录 | 含「结果只进图片墙」这类画布没变的操作（DoD ⑤） | 用户在编辑记录里要找得到自己刚才那一下 |
| 但撤销时跳过它们 | 一路往前找真正动过画布的那条 | 重复设一个已经成立的值，不该让「按了撤销没反应」 |
| 历史列表不含快照 | 只回 seq / label / changed / created_at | 十几条 before+after 就能把响应撑到几百 KB，而前端要的只是「刚才做了什么」 |
| 标签用**结果说明**而非工具名 | 「图层已改名为「顶层」」而不是「改名」 | 连着三次改名在历史里是三条一模一样的「改名」，用户分不出要退到哪一步 |
| UI 改动也走工具入口 | 面板的显示/隐藏、设为当前图改为调工具 | 直接改文档的路径不写历史，用户会发现「有些操作退不回去」 |
| 裁剪同时同步显示尺寸 | crop 与 transform.width/height 一起改 | 否则把 100×100 的裁剪区拉满原本 1000×1000 的框，那是缩放不是裁剪 |
| crop 四字段都是整数 | 对准素材 pixel 网格 | 允许 3.7 像素的裁剪窗口除了让人困惑没有别的用处 |
| **不升 `DOC_VERSION`** | 新字段全带默认值 | 升版本会让存量会话全部读不进来，还得写一遍洗数据迁移 |
| DoD ③ 落在前端纯函数 | `domain/pixels.ts` 只写 RGB，从不写第 4 个字节 | 服务端 Pillow 那类实现的坑是 `convert('RGB')` 丢 alpha；这里从循环体里就没留 alpha 的左值 |
| 调色不走 Konva filters | 离屏 canvas + 纯函数 | Konva 自定义 filter 靠 `this` 绑定读节点属性，失效表现是「调色突然没效果」，极难排查 |

> M5 计划里写的是「22 个 spec」，当前 16 个：抠图（`remove_background`）、
> 局部重绘（`inpaint`）、超分这类**要动像素**的工具依赖 M6 选区与 M7 拆层，
> 本阶段不注册空壳。它们进来时同样只是注册表里加一行 + 一个像素服务。

### M9 · ★★ 差异化三件套（简历杀手锏）

> 顺序有讲究：**CoT → 状态机 → 可观测**。CoT 成本最低、演示效果最强，先做。

#### M9.1 · Agent 思维链（CoT）流式输出 · 2 人天

| 项 | 内容 |
|---|---|
| 设计 | 新增 SSE 事件 `cot`，与 `progress` 并行推送。`kind` 分四类：`thought` / `tool_call` / `observation` / `reflection` |
| 实现 | `agent/llm.py` 挂 LangChain 回调，planner 流式 token → Redis Pub/Sub → SSE；tool 执行前后各发一条 `observation` |
| 前端 | `components/agent/CoTStream.tsx` —— 可折叠的思考过程面板，与进度条并列 |
| 坑 | 推理模型的 `reasoning_content` 与 `content` 是**两个字段**，别只透传一个；流式 chunk 要做 delta 拼接，别整段覆盖 |
| DoD | ① 用户能看到模型实时「思考」过程；② 思考流与进度条不互相阻塞；③ 断线重连后不重复渲染已收到的 token |

#### M9.2 · 真 LangGraph 状态机 + 反思循环 + 断点续跑 · 3–4 人天

| 项 | 内容 |
|---|---|
| 图结构 | `plan → verify → execute → observe → (条件边)` ；失败时 `→ reflect → replan`（错误回灌，重规划**剩余**步骤）；成功或重试超限 `→ END` |
| State | `{messages, instruction, plan, cursor, tool_results, errors, retry_count, revision, cot_buffer}` |
| checkpointer | `langgraph-checkpoint-postgres`，`thread_id = agent_run_id` |
| ★ 点睛 | **把人机确认做成 LangGraph 的 interrupt**：确认态就是一次图中断，状态由 checkpointer 落地，用户点「确认」后 `resume` 继续跑。这是参考项目「转 QUEUED + 手动点」做不到的——也是「你真的用了 LangGraph」的硬证据 |
| 坑 | 参考项目踩过：`langgraph-checkpoint-postgres` 装了却没用；**State 只保留 Annotation 声明过的 channel**，未声明的 key 会被静默丢弃 |
| DoD | ① 工具失败后模型能看见错误并重新规划；② 服务重启后未完成的 run 能 resume 继续；③ `retry_count` 达上限后优雅降级为 partial_failed 而非死循环 |

#### M9.3 · 全链路 trace + 可观测指标 · 1–2 人天

| 项 | 内容 |
|---|---|
| 实现 | 每次 `respond()` 打一条 Langfuse trace：`planner prompt 版本` / `tool_calls` / **校验失败原因** / 每步耗时与 token |
| ★ 指标 | 把 **「计划校验拒绝率」** 做成核心可观测指标——这是衡量 Agent 稳定性的关键，多数人想不到 |
| DoD | ① 任意一次对话能回溯完整 trace；② 有面板能看到拒绝率趋势；③ prompt 改版前后可对比 |

### M10 · 工程化：评测 + CI + Prompt Regression · 3 人天

| 项 | 内容 |
|---|---|
| Agent 评测集 | `app/eval/` 做 `{指令 → 期望工具序列}`：**照抄参考项目的评测框架外壳，但换成规划指标**（它的 eval 只测像素工具） |
| 指标 | tool-F1 / 序列精确匹配 EM / 参数槽位准确率 / 计划校验通过率 |
| CI | GitHub Actions：services 起 PG17 + Redis7 + silo（**必须带 healthcheck**）→ `uv sync` → alembic → pytest |
| ★ Prompt Regression | `agent/prompts.py` 建版本快照，每次改 prompt 跑一遍评测集，**EM 低于基线则 fail** |
| 坑 | 测试用**独占 Redis DB 1**（开发 worker 只听默认库，不会抢任务）；测试用户统一 `test_` 前缀并定向删除，绝不误清开发库 |
| DoD | ① `cases.json` ≥ 30 条；② CI 全绿；③ 故意改坏 prompt 能让 CI 挂掉 |

## 三、SSE 事件协议（M2 定死，后续只增不改）

| type | payload | 首发阶段 |
|---|---|---|
| `snapshot` | `{run_id, status, steps[], progress}` | M2 |
| `progress` | `{run_id, progress, stage, message}` | M2 |
| `step` | `{run_id, step_id, status, progress, stage}` | M8 |
| `plan` | `{run_id, steps[{id,tool,params,depends_on,status}], needs_confirm}` | M8 |
| **`cot`** | `{run_id, seq, node, kind, delta}` — kind ∈ `thought`/`tool_call`/`observation`/`reflection` | M9.1 |
| `result` | `{run_id, asset_id, url, wall_only}` | M2 |
| `error` | `{run_id, step_id, code, message, recoverable}` | M2 |
| `done` | `{run_id}` | M2 |
| `ping` | `{}` — 15s 心跳 | M2 |

帧格式沿用 `data:{...}\n\n`；**状态码必须 200**（201 会导致部分反代不 flush）；600s 主动断开让客户端重连。

## 六、风险登记

| 风险 | 影响 | 应对 |
|---|---|---|
| CV 依赖（rembg/onnxruntime）体积大、安装慢 | 阻塞本地开发 | 走 optional extra，默认不装；`_cv_inpaint` 降级路径保证功能不残废 |
| Alpine 下 onnxruntime 崩 | 构建期看不出来，运行时才炸 | 基础镜像用 **Debian 系**（`python:3.13-slim` 已是，勿换 alpine） |
| 规划模型不稳定，计划质量波动 | 演示翻车 | M10 的 prompt regression + 拒答阈值；演示前固定 prompt 版本 |
| 端口冲突导致「明明配置对却连不上」 | 排查方向完全跑偏 | 切项目前先 `down`；`docker ps` 确认 |
| 上下文过长导致 planner 退化 | 多轮后规划变蠢 | 只回灌**最近 N 步**执行结果给 reflect 节点，不灌全历史 |
| 时间不够做完全部 M9 | 差异化缺失 | CoT（M9.1）性价比最高且最先做；状态机可只做 interrupt 不做反思循环 |
